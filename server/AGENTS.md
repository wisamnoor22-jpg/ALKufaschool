Project Name

AlKufaSchool — برنامج مدرسة الكوفة الذكي

Project Purpose

هذا نظام إدارة مدرسي احترافي وطويل الأمد لمدرسة الكوفة الأهلية.يجب التعامل معه كمنتج حقيقي قابل للتطوير، وليس كمشروع تجريبي أو مؤقت.

Structure Meaning

src/: الواجهة الأمامية React.

public/: الملفات العامة والصور والشعارات.

server/: الخادم الخلفي Express وملفات قاعدة البيانات والمسارات والخدمات.

dist/: ناتج بناء الواجهة، ولا يُعدّل يدويًا.

node_modules/: الحزم المثبتة، ولا يُعدّل يدويًا.

لا يوجد مجلد باسم client.

عند الإشارة إلى الواجهة الأمامية استخدم المسار src/.

عند الإشارة إلى الخادم استخدم المسار server/.

Frontend source: src/

Backend: Node.js + Express

Backend source: server/

Version Control: Git + GitHub

Main branch: main

Core Working Rules

اقرأ بنية المشروع والملفات المرتبطة قبل تنفيذ أي تعديل.

لا تحذف أو تعطّل أي ميزة موجودة إلا إذا طلب المستخدم ذلك صراحة.

لا تعدّل ملفات غير مرتبطة بالمهمة دون ضرورة واضحة.

حافظ على React + Vite في الواجهة وExpress في الخادم وPostgreSQL في قاعدة البيانات.

لا تستبدل PostgreSQL بقاعدة بيانات أخرى.

لا تفترض وجود مجلد client.

استخدم src/ لكل ملفات الواجهة الأمامية.

استخدم server/ لكل ملفات الخادم الخلفي.

لا تعدّل dist/ أو node_modules/ يدويًا.

حافظ على أسماء المسارات والجداول والواجهات الحالية قدر الإمكان.

عند وجود أكثر من حل، اختر الحل الأبسط والأكثر أمانًا والأقل تأثيرًا على المشروع.

لا تنفذ تغييرات تجميلية عامة أو إعادة هيكلة واسعة دون طلب صريح.

لا تنشئ بيانات وهمية داخل النظام النهائي إلا للاختبار المؤقت، ويجب حذفها بعد الاختبار.

لا تعرض أو تسجل كلمات المرور أو مفاتيح الوصول أو محتوى ملف .env.

لا تقل إن المهمة اكتملت إذا بقي جزء غير منفذ أو غير مختبر.

Before Making Changes

افحص حالة Git:

git status

تحقق من الفرع الحالي:

git branch --show-current

يجب أن يكون الفرع main ما لم يطلب المستخدم غير ذلك.

افهم الملفات المتأثرة والعلاقات بينها.

افحص الملفات الحالية قبل إنشاء ملفات جديدة.

اشرح باختصار خطة التنفيذ قبل أي تعديل كبير.

إذا كان هناك خطر على البيانات أو بنية قاعدة البيانات، اذكر ذلك بوضوح قبل التنفيذ.

قبل تعديل كبير، ذكّر المستخدم بإنشاء نسخة احتياطية على GitHub.

Code Change Standards

اكتب كودًا واضحًا ومنظمًا وسهل الصيانة.

تجنب تكرار المنطق بين الملفات.

حافظ على أسلوب الكود الموجود في المشروع.

استخدم معالجة أخطاء مناسبة في الواجهة والخادم.

تحقق من المدخلات قبل إرسالها إلى قاعدة البيانات.

استخدم parameterized queries لمنع SQL injection.

لا تغيّر أسماء API الحالية دون ضرورة واضحة.

لا تكسر الصفحات أو الميزات الموجودة.

عند إضافة API جديد، اربطه فعليًا في نقطة تشغيل الخادم المناسبة داخل server/.

عند إضافة صفحة أو مسار واجهة جديد، اربطه فعليًا في نظام التوجيه والقائمة المناسبة داخل src/.

لا تنشئ ملفًا جديدًا إذا كان هناك ملف موجود يؤدي الغرض نفسه.

لا تنقل الملفات أو تعيد تسميتها دون حاجة واضحة.

لا تعدّل ملفات build الناتجة داخل dist/.

لا تعدّل الحزم داخل node_modules/.

لا تستخدم localStorage كبديل لقاعدة البيانات للبيانات الأساسية.

حافظ على التوافق بين الواجهة والخادم وقاعدة البيانات.

server/

أنشئه في المسار المناسب داخل server/.

عند إضافة controller أو service:

لا تكرر منطقًا موجودًا.

استخدم الخدمات الحالية عند توفرها.

استخدم رموز HTTP الصحيحة.

أعد رسائل خطأ واضحة وآمنة.

لا تعرض stack trace أو بيانات حساسة للواجهة.

تحقق من جميع المدخلات القادمة من الواجهة.

لا تحذف route حاليًا أو تغيّر عقده دون طلب صريح.

لا تفترض نجاح اتصال قاعدة البيانات دون اختباره.

Database Rules

جميع البيانات الدائمة يجب أن تُخزن في PostgreSQL.

لا تستخدم قاعدة بيانات بديلة.

قبل إنشاء جدول جديد، تحقق من عدم وجود جدول يؤدي نفس الغرض.

استخدم قيودًا مناسبة عند الحاجة:

PRIMARY KEY

FOREIGN KEY

UNIQUE

NOT NULL

لا تحذف جداول أو أعمدة أو بيانات دون طلب صريح.

أي migration أو SQL جديد يجب أن يكون واضحًا وآمنًا.

استخدم معاملات transaction عند تنفيذ عمليات مترابطة وحساسة.

استخدم parameterized queries دائمًا.

حافظ على العلاقات الحالية بين الجداول.

لا تغيّر نوع عمود أو اسمه دون فحص جميع الملفات التي تعتمد عليه.

امنع تكرار رسوم نفس المرحلة في نفس السنة الدراسية.

استخدم متغيرات البيئة الحالية:

DB_USER

DB_HOST

DB_NAME

DB_PASSWORD

DB_PORT

لا تعرض قيم متغيرات البيئة.

إذا احتاج التعديل SQL يدويًا، قدّم الملف أو الأمر بوضوح ولا تدّعِ تنفيذه إذا لم يُنفذ.
